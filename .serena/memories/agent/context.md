# Agent Context

- Startup flow for coding tasks: activate Serena project, read Serena initial instructions if not already read, read `mem:core`, then load only domain memories relevant to the requested change.
- Boost-first Laravel workflow: call `application-info` early when versions matter; use `search-docs` before Laravel ecosystem code changes; use `database-schema` before DB/model/query work; use `database-query` for read-only DB inspection; use `browser-logs`, `last-error`, and `read-log-entries` before guessing runtime failures; use `get-absolute-url` before sharing app URLs.
- Serena role: memory graph for stable project facts, symbolic navigation for source code, and targeted reads instead of whole-file scans when symbol context is enough.
- Shell role: Artisan commands, package scripts, git status/diff, and fast search with `rg`.
- Mandatory skill usage: before substantial work, inspect available project skills and activate every skill whose `description` matches the task. Skill frontmatter is the source of truth; `AGENTS.md` is not a complete skill inventory.
- Skill inventory maintenance: keep full skill instructions in each `SKILL.md`; ensure new skill frontmatter descriptions have clear triggers and exclusions; avoid complete skill lists in `AGENTS.md`; regenerate `AGENTS.md` after guideline changes.
- Efficiency rule: load the smallest relevant docs, memories, and skill files; avoid bulk-reading all project skills unless the task is explicitly about skill inventory.
- Implementation/refactor flow: inspect `git status --short`; classify the task domain; load minimal context; inspect sibling patterns; search references before changing public methods, routes, controller actions, request payloads, component props, or generated types; preserve behavior during refactors unless explicitly requested; keep generated files generated.
- Thin controller/action pattern: controllers should handle binding, authorization, validation handoff, action invocation, and HTTP/Inertia responses. Move business logic to `app/Actions/{Domain}` for multi-step writes, transactions, branching workflows, external services, events, storage, complex Eloquent mutations, or reused logic. Prefer `Create{Model}`, `Update{Model}`, `Delete{Model}` action names for `store`, `update`, `destroy`; use `handle(...)`; keep responses in controllers.
- Serena memory management: use `mem:core` as entry point; read `mem:memory_maintenance` before memory restructuring; add/update memories only for stable, non-obvious project facts; never store task-local notes, secrets, private data, volatile line-level details, or generic framework knowledge; link new memories from a parent memory with `mem:` references.
- Project docs/task tracking: do not create docs unless requested; if `docs/PRD.md`, `docs/TASKS.md`, or similar docs exist, read relevant sections during intake. Current user instructions override stale docs. Treat PRD as product intent/acceptance criteria and TASKS as execution checklist. Check off tasks only after implementation is complete, verification passes, and the result is stable; annotate blocked/superseded items instead of marking them complete.
- Verification rule: follow `mem:task_completion`; no behavior change is complete without focused automated checks unless the change is configuration/docs-only. After broad implementations, refactors, or cross-domain changes, prefer `composer run ci:check` before handoff when time permits; otherwise report the focused checks that were run and the skipped broader CI check.
